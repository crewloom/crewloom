# بروتوكول: execution-pipeline (خط التنفيذ)

النسخة الإنجليزية هي المرجع: [`PROTOCOL_EXECUTION_PIPELINE.md`](PROTOCOL_EXECUTION_PIPELINE.md). النوع: Protocol (انظر [`ARTIFACT_TAXONOMY.ar.md`](ARTIFACT_TAXONOMY.ar.md)). الحالة: **مكتوب، استرشادي**. اللي بيشتغل النهارده بس هو المعلَّم *exists*؛ مُحقِّق holdout وفحص نطاق الـ diff ومولّد التقرير وسجل الإفلات *مخطط لها* ومش مبنية.

الغرض: إن الإيجنت يبقى دقيق في أي مهمة برمجية في أي مشروع، حتى لو النموذج تحته ضعيف. الباني اللي بيكتب الفحص وبعدين يعدّيه مينفعش يتحقق من نفسه، فالبروتوكول بينقل التحقق لمهارات وأدوات وقواعد الباني مبيتحكمش فيها. البروتوكول مش مربوط بتطبيق ولا stack معيّن.

## المكوّنات (البروتوكول هو الأجزاء دي مش نص)

| النوع | المكوّن | بيملك |
|---|---|---|
| Skill | `.agent/skills/crewloom-execution-pipeline` | تشغيل الخطوات الخمس، وزن المهمة، العمق، قواعد الوقوف |
| Skill | `.agent/skills/crewloom-pin-before-change` | الخطوة 2: اختبارات تثبيت السلوك مع إثبات إنها تقدر تفشل |
| Skill | `.agent/skills/crewloom-adversarial-verify` | الخطوة 4: sabotage-red ومراجعة الادعاء قصاد الكود وملاحظات بدليل بس |
| Tool | `scripts/exec-gates.mjs` *exists* | كشف الـ stack وتشغيل build وtypecheck وlint وtest وبوابة الوعود؛ بيطبع الدليل وبيعلّم البوابة اللي معرفش يشغّلها `NOT-RUN` |
| Tool | `scripts/promise-ledger.sh` *exists* | بوابة الوعود (`ENGINEERING-PROTOCOLS.md` §2.8)، بيشغّلها hook الـ Stop |
| Tool | `scripts/check-architecture.mjs` *exists* | فحص اتجاه الاعتماديات |
| Rule | القواعد تحت | اللي ممنوع أي خطوة تتخطاه |
| مخطط | مُحقِّق holdout، فحص نطاق الـ diff، مولّد التقرير، سجل الإفلات | مش مبنية |

```
name:        execution-pipeline
trigger:     الإيجنت اتطلب منه يبني أو يعدّل أو يصلّح أو يعيد هيكلة أو ينقل أي برنامج، في أي مشروع فرعي أو أي مشروع المشغّل يشاور عليه
steps:
  1. UNDERSTAND  صنّف المهمة (build | feature | fix | refactor | migrate). ارسم خريطة الكود اللي بتلمسه ومن بيستدعيه. قسّم الطلب لوعود من سطر واحد لكل وعد شرط نهائي (Promise Ledger، ENGINEERING-PROTOCOLS §2.8). سجّل كل افتراض؛ اسأل المشغّل بس لو الإجابة هتغيّر شرط نهائي.
  2. PIN         قبل تعديل كود موجود، اكتب اختبارات تثبّت سلوكه الحالي وشغّلها خضرا. الإصلاح يبدأ بإعادة إنتاج حتمية حمرا (BDRP). الكود الجديد يبدأ باختبارات الوعود فاشلة للسبب الصح.
  3. CHANGE      أصغر تغيير يحقق الوعود. إعادة الهيكلة وتغيير السلوك في commits منفصلة. ابقَ جوه الملفات اللي في الخريطة؛ أي حاجة تانية تتبلّغ ومتتعدّلش.
  4. PROVE       شغّل بوابات المشروع بـ `scripts/exec-gates.mjs`: build وtypecheck وlint من غير تحذيرات واختبارات وفحص معمارية المستودع. شغّل كل اختبار وعد وكل اختبار مثبَّت. Sabotage-red لكل وعد (احذف أو عطّل التنفيذ، الاختبار لازم يحمرّ، ثم رجّعه). شغّل فحوص holdout بتاعة المُحقِّق المستقل، والباني ميشوفهاش.
  5. DELIVER     الـ harness يولّد التقرير من أدلة البوابات: اللي اتشغّل بنتيجته الحقيقية، واللي ماتشغّلش أو ماتحققش منه، والافتراضات المفتوحة، ونطاق الـ diff. الباني مبيعدّلش حكم التقرير.
exit:        كل وعد له اختبار ناجح بدليل sabotage-red، وكل اختبار مثبَّت لسه أخضر، وبوابات الملف عدّت، وفحوص holdout عدّت، والتقرير اتولّد
on_failure:  البوابة الفاشلة بترجّع مهمة إصلاح محددة (ملف، سطر، مدخل فاشل) للباني. نفس السبب مرتين يوقف الأسلوب ده: غيّر الاستراتيجية (قسّم المهمة، أو صعّد حسب PROTOCOL_MODEL_ESCALATION، أو اسأل المشغّل). أكتر من محاولتين على نفس السبب: وقّف وبلّغ بالعائق والدليل. ممنوع تقرير نجاح وفيه بوابة مفتوحة.
enforced_by: جزئي. موجود: scripts/exec-gates.mjs وscripts/promise-ledger.sh (hook الـ Stop) وscripts/check-architecture.mjs؛ المهارات التلاتة استرشادية. مخطط: مُحقِّق holdout، فحص نطاق الـ diff، مولّد التقرير. لسه مش متوصّل يشتغل أوتوماتيك.
owner:       النسخة الإنجليزية من الملف ده؛ ميكانيكا الوعود في docs/architecture/ENGINEERING-PROTOCOLS.md §2.8
```

## أدوار Crewloom

الأدوار مفصولة بالوظيفة، واللي بيبني مبيوافقش. كل دور مربوط بفريق موجود في [`SKILLS_AND_TEAMS_CATALOG.md`](SKILLS_AND_TEAMS_CATALOG.md)؛ مفيش نوع إيجنت جديد.

| الدور | بيعمل إيه | الفريق |
|---|---|---|
| Planner | الخطوة 1 ومذكرة التصميم | Architecture & Planning |
| Builder | الخطوتين 2 (كود جديد) و3 | فريق المجال للملفات المتأثرة |
| Verifier | اختبارات التثبيت وفحوص holdout وsabotage-red والخطوة 4 | QA & Debugging |
| Reviewer | يقرأ الـ diff ويقارن الـ README بالكود؛ كل ملاحظة لازم ملف وسطر وإلا تتشال | QA & Debugging، من عائلة نماذج غير عائلة الـ Builder |
| Releaser | الخطوة 5 والإصدار (AGENTS.md § Mandatory Release Protocol) | `crewloom-release-verifier` |

نموذج واحد صغير ممكن يلعب كذا دور بالتتابع. ممنوع يكون هو اللي كتب اختبار الوعد وهو الحكم الوحيد عليه: فحوص holdout وsabotage-red هي الجزء المستقل.

## أنواع المهام

نفس الخطوات الخمس بوزن مختلف.

| النوع | الوزن على | بيعيد استخدام |
|---|---|---|
| build | الوعود والاختبارات قبل الكود | FEP |
| feature على كود موجود | PIN: من غيره مفيش حاجة تبيّن إن التغيير كسر شيء | FEP، وASDP لو الحدود اتحركت |
| fix | إعادة الإنتاج الحمرا والـ 5-Whys | BDRP |
| refactor | إثبات إن السلوك ما اتغيرش: نفس الاختبارات المثبَّتة قبل وبعد | قواعد FEP الهيكلية |
| migrate | expand وcontract، وكل خطوة قابلة للتراجع | ASDP |

## العمق

نوع المهمة بيحدد المسار، والمخاطر بتحدد العمق. درجة مخاطر حتمية (مش رأي نموذج) بتزوّد العمق لو التغيير بيلمس: الأمان أو بيانات الاعتماد أو التشفير؛ تخزين دائم أو حذف؛ حد نظام (شبكة، ملفات، جسر native، عملية فرعية)؛ ادّعاء جديد في README أو الواجهة؛ أو منطقة مذكورة في سجل الإفلات. إصلاح من سطر واحد قليل المخاطر يمشي UNDERSTAND وCHANGE وPROVE مخفّف. المخاطر العالية تضيف Reviewer مستقل من عائلة نماذج مختلفة ومجموعة holdout كاملة.

## ملفات التقنية

`scripts/exec-gates.mjs` بيكتشف الـ stack من ملفات المشروع (Node وFlutter وRust وGo وPython) وبيشغّل بواباته. المشروع يعدّل أو يضيف على الكشف بـ `.crewloom/profile.json` (`{"gates": {"test": "..."}}`)؛ والـ stack المجهول محتاج الملف ده والمشغّل يأكده مرة. المهارات مبتكتبش أوامر stack جواها. صرامة الـ lint الخاصة بالـ stack (زي منع كتم الـ lint الشامل) مكانها الملف أو إعدادات المشروع نفسه، مش البروتوكول ده.

## ترتيب الدليل

الأفضلية بالترتيب: فحص اتنفّذ (اختبار حمرّ ثم اخضرّ، تشغيل sabotage)، ثم أداة حتمية (analyzer، type checker)، وبعدها بس حكم نموذج. ملاحظة نموذج من غير ملف وسطر تتشال. متحوّلش فحص ممكن برنامج ينفّذه لرأي.

## سجل الإفلات

كل عيب يتلاقي بعد التسليم يتسجّل بمنطقته والخطوة اللي كان لازم تمسكه. فحص مخصص مبيتضافش إلا لما نفس العيب يفلت مرتين (ENGINEERING-PROTOCOLS §2.8 بند 5). فحص مبيمسكش حاجة خلال عدد محدد من المهام ينزل لمسار أخف عشان التكلفة متكبرش بلا حد. الملف المخطط: `.crewloom/ledger/escapes.json`.

## ثوابت Crewloom اللي البروتوكول بيحافظ عليها

- **Zero-Destruction** (الدستور مادة III): PIN وCHANGE بيعدّلوا في مكانه؛ حذف أو نقل ملف يحتاج نسخة احتياطية ومحوّل. Sabotage-red بيرجّع التنفيذ اللي شاله.
- **لا تلفيق** (AGENTS.md § Non-negotiable 3؛ الدستور مادة VII): التقرير بيسرد بس الأوامر اللي اتشغّلت بمخرجاتها الحقيقية، وبيقول اللي ماتحققش منه.
- **سيادة المشغّل**: المشغّل بيوافق على الوعود وأي تغيير نطاق. الرسائل والنشر والمشتريات وإعادة كتابة التاريخ لسه محتاجة تفويض صريح.
- **ثنائي اللغة**: نصوص الواجهة في أي تغيير تعدّي على قواميس i18n، واللغتين بتتحقق في شغل الواجهة.
- **الإصدار**: التغيير المتحقق منه بينتهي بتدفق الإصدار في AGENTS.md والـ CI بيتفحص بـ `gh` مش بالسكرابينج.
- **ترتيب الأسبقية** (الدستور مادة VI): الدستور ثم AGENTS.md ثم البروتوكول ده.

## الحدود

- مفيش حاجة هنا اتقاست. المجهول: زمن البوابات وتكلفة التوكنز حسب حجم المهمة، وكام عيب مزروع بيمسكه الخط، وكام مرة بوابة بتعطّل شغل سليم. أول قياس مخطط هو benchmark عيوب مزروعة من عيوب حقيقية فلتت في كذا مشروع وكذا stack؛ متدّعيش فعالية قبله. `exec-gates.mjs` اتجرّب على `bridge/` (Node) ومشروع Flutter واحد بس؛ باقي الـ stacks مش مجرّبة.
- PIN بجودة الاختبارات اللي الإيجنت بيكتبها على تغطية ضعيفة. Sabotage-red هو اللي بيكشف الاختبار الدائري؛ متشيلوش توفيرًا للوقت.
- Reviewer من عائلة نماذج تانية بيقلل الأخطاء المترابطة ومبيلغيهاش. بيكمّل الفحوص المنفّذة ومبيحلّش محلها.
- موافقة المشغّل على كل وعد ممكن تبطّأ المهام الصغيرة. مسار موافقة مسبقة للمهام قليلة المخاطر مخطط ومش معرَّف.
